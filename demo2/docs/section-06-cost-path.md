# Section 06:成本與導入路徑

## 段落定位

**存在理由**:創辦人的第二個問題 —— 要花多少錢、多久、誰負責。
但這段真正的功能不是報價,是把主軸**兌現成商業價值**:
評測不只是品管,**它是你敢不敢降級省錢的依據**。沒有評測表,你不敢降;有評測表,降完跑一次就知道品質掉了沒。
最後回到開場那兩段文案收束全場。

**討論方向**:問題導向 + 收束。公式而非數字、槓桿而非清單、路徑而非願景。

## 內容要點

1. **成本公式**(新知):
   單次成本 =(input_tokens × 單價_in + output_tokens × 單價_out)÷ 1,000,000
   月成本 = 單次 × SKU 數 × 每 SKU 重生成次數 ×(1 + judge 開銷比)
   **投影片上不寫價格數字** —— 模型和價格每季都在動,今天寫上去下個月就過期,
   然後你們拿著錯的數字做預算。公式不會過期,金額由 demo 當場印出來。
2. **評測本身要花錢**(新知,最常被漏算的一筆):judge 呼叫是額外成本,而且它用的模型通常比生成更貴。
   這次跑的實際佔比由 demo 當場印出,不寫死在投影片上。
3. **降本四招**(新知):模型選型降級(通常最大一筆,**代價是要有評測表才敢降,否則是在賭**)、
   Batch API(約 5 折,延遲變小時級,文案本來就不急)、Context caching(input token 大幅折扣,前綴要夠長)、
   結果快取(最被低估:**商品規格沒變就不要重新生成**,很多團隊每天全量重跑,九成商品根本沒動過)。
4. **這套東西到底用到哪些 GCP**(新知,預防針):
   誠實說,今天 demo 只真的用到兩個服務 —— GEAP 和 BigQuery,圖上實線只有這兩個,其餘全部虛線。
   這是刻意的:**先把「怎麼知道它變好了」解決掉,再談怎麼部署。**
   順序反過來的專案,通常上線後才發現沒人能判斷好壞,回頭補評測成本高得多。
   虛線那些(Cloud Run、Scheduler、Secret Manager、VPC-SC)都是標準雲端工程,你的工程師本來就會;
   **真正難的是實線那兩個框裡面發生的事。**
5. **90 天路徑 + 收尾**(新知 + 回收):
   Studio 驗證可行性 2 週 → 建 golden set + API 串接 4 週(**30–50 筆就足以開始**)→ 小流量上線 + 監控 6 週。
   收尾回到開場那兩段文案:現在你有辦法說出哪個比較好,而且能證明 —— 不是「感覺比較順」,是一張表。
   三件事帶回去:先建規則層(它免費)、用 API 原生的 structured output、評測本身要花錢記得算進去。

## 備註要點

- **銜接**:接第五段 —— 那這套流程要花多少錢?
- 第 1 頁:先講為什麼不寫價格數字,再講評測要花錢。**不要唸投影片上不存在的金額。**
- 第 3 頁:虛線 = 上線才需要,與 diagram-04-3 同一個約定。這頁是預防針 ——
  不主動講的話 QA 一定有人問「這跟 GCP 有什麼關係」,被動回答會顯得心虛。
- 第 5 頁:三件事帶回去要唸得慢。第一件事回收 80%/2%/0% 那條線,第三件事回收 demo 印出的 judge 佔比。
- **交棒**:「謝謝。接下來我實際跑給大家看。」—— 收尾之後才進 demo,順序不要顛倒。
