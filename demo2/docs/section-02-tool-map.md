# Section 02:GCP 工具地圖

## 段落定位

**存在理由**:聽眾席上的創辦人此刻最急的問題是「這麼多 Google 的 AI 產品,我到底該用哪個」。
不先把這個焦慮處理掉,他們沒有餘裕聽後面的 prompt 與評測。
但這段**不是產品介紹** —— 它替主軸做兩件事:(1) 建立「探索/整合/上線」的階段語言,
讓第三、四段的內容有地方掛;(2) 在第三層留下一個空格 —— 上線期需要「一組固定的題目和一套固定的評分方式」,
那個空格就是後面兩段要填的東西。

**討論方向**:對比取捨。不逐一介紹產品,改用「你在哪個階段用哪個」組織,每一層用一句
「對創辦人而言這代表什麼」收尾 —— 這是照顧混合聽眾的機制,同一件事講兩個層次,而不是交替講商業和技術。

## 內容要點

1. **三層地圖總覽**(新知):依階段而非產品線切。探索期 / 整合期 / 上線期。
2. **探索期 = GEAP Studio**(新知):瀏覽器打開就能用,不寫程式,五分鐘判斷這事做不做得成。
   → 對創辦人:這一層應該你或 PM 自己做,不要先排工程資源。
   → 對工程師:Studio 調好的 prompt 可以直接匯出成程式碼。
   **這裡順帶交代改名**:Vertex AI 於 2026-04 Cloud Next 更名 Gemini Enterprise Agent Platform(GEAP),
   五月底遷移完成,**但 API 端點與 SDK 參數完全沒動**(demo 裡 `vertexai=True` 還在)。
   不先交代,台下會以為在講另一個產品。
3. **整合期 = Gemini API vs GEAP 怎麼選**(新知,全段資訊密度最高):
   兩邊背後同一批模型,差別不在模型在周邊 —— 認證、計費歸屬、資料落地、VPC-SC、稽核日誌。
   → 對創辦人:這是部署決策不是技術決策。切換只差 client 建構參數,所以不用一開始就糾結;
   但原型做太久、資料都在個人帳號下,搬家會很痛。
4. **上線期 = 評測與監控**(新知,故意留白):這一層大部分人直接跳過,三個月後付出代價。
   工具其次,重點是有沒有一組固定的題目和一套固定的評分方式。
   → 對創辦人:這是你唯一能拿來對董事會證明「有進步」的東西。
5. **銜接**(轉折):同樣的工具,為什麼有人做得起來、有人做不起來?

**刪除/置換的點**:
- 原版第 2 頁是 GEAP 主控台截圖疊三個 SVG 標註圈。這裡改成**左欄三個重點文字 + 右欄截圖**,
  理由:Marp 的圖片是內容區塊,疊座標標註要另外手刻 SVG 包住點陣圖,成本高且換圖就要重量座標。
  改名那句話仍然指著螢幕講,說服力不變。
- 原版在這頁順帶預告 Authenticate 卡片(ADC vs API key)鋪下一頁 → 保留,用口述(備註),不佔版面。

## 先備知識

- 聽眾:知道 GCP 是雲端供應商即可。**不需要**知道 Vertex AI 這個舊名 —— 本段自己交代改名。
- 講者:**需要事前補強** GEAP 改名後的商務條款細節(資料落地承諾、計費歸屬、DPA 簽署對象)。
  被問到不確定的就說「這我要查」,不要在台上編 —— 台下有工程師。

## 備註要點

- **銜接**:接第一段的因果鏈圖 —— 「先講工具,因為選錯工具後面全部白做」。
- 第 2 頁:第一次講到 GEAP 就先交代改名,**指著截圖上那句 "Vertex AI is now Agent Platform" 講**,
  比自己說有說服力。強調端點與 SDK 沒改,程式碼一行都不用動。
- 第 3 頁是全段最慢的一頁,給足 3 分鐘。關鍵句:切換只差 client 的建構參數。
- 第 4 頁刻意留白 —— 不要在這裡開始講評測方法,那是第四段。
- **交棒**(第 5 頁):同樣的工具為什麼有人做得起來 → 因為他們把要求寫成了規格。
