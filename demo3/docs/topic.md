# 你怎麼知道它變好了? 主軸設計

## 主軸說明

**主題**:你怎麼知道它變好了?
**副標**:一條零售文案 pipeline 的四次改版

核心訊息(聽眾走出場只要記得這一件事):

> **生成式 AI 的難處不在叫模型,而在你怎麼知道它有沒有變好。**

整場是一條敘事線:現場先為「哪篇文案比較好」分裂 → 承認我們沒有共同的判準 →
四版 prompt 每版只加一件事,讓改善可歸因 → 三層評測把「好」變成可量測的東西 →
數字回頭打臉,四版裡只有一版統計成立 → 實機跑一次 → 帶走第一個評測迴圈。
每段結束前回扣一次核心訊息。

訪談時提出三組,使用者選定 A。

| 方案 | 主題／副標 | 大綱骨架 | 採用/未採用理由 |
|---|---|---|---|

| B | Demo 很美,上線很痛／生成式 AI 的最後一哩 | 禁詞罰則開場 → 三種上線前才發現的痛 → 規則層 → 評審層 → demo → 上線前五項檢查 | 情緒強度最高(食安法 §28 罰 60–500 萬),但把全場壓在風險上,方法論反而變成配角 |

## 聽眾輪廓

- **範圍規模**:新創加速器場,約 40–60 人;創辦人／PM 與工程師大約各半
- **技術能力**:mixed —— 不預設任何人有 ML 背景,但台下一定有工程師會抓細節
- **已知**:LLM 會寫文案、多半玩過 ChatGPT;知道 GCP 是雲端供應商;知道「上線要小心」但講不出小心什麼
- **未知**:
  - 不知道「評測」是可以工程化的東西,更不知道評測本身會產生可觀成本
  - 不知道 rubric 用二元判準與用 1–5 分的差別在哪
  - 不知道台灣廣告法規禁詞(食安法 §28)會直接變成上線風險
  - 不知道「A 版比 B 版高 3%」多數時候是雜訊而不是進步
- **兩種聽眾各自要帶走的**:
  - 創辦人／PM — 我怎麼知道這東西能不能上線、會不會出事;要花多少錢、多久、誰負責
  - 工程師 — 評測迴圈怎麼建、二元 rubric 怎麼寫、judge bias 怎麼壓、顯著性怎麼算

## 講者先備知識

素材全部是講者自己跑出來的:四版 prompt、三層評測、200 筆評測集(demo 取前 50 筆)、
真實成本帳、離線重播 fixtures。

- **想突顯**:工程實作細節 —— 不迴避技術深水(structured output、二元 rubric、
  judge self-preference bias、配對比較的 95% CI)。這是本場與「又一場 AI 分享」的分界。
- **要事前補強**:GEAP(Vertex AI 2026-04 改名)改名後的商務條款細節(資料落地、計費歸屬)。
  台上被問到不確定的就說要查,不編。
- **刻意避開**:模型內部原理、fine-tuning、RAG 架構深潛 —— 這場不談。
- **可信度資產**:願意講踩過的坑 —— rubric 生成時沒告知通路字數預算,導致出現
  「30 字賣點塞不下」的判準,修正前 v0 拿 100%、v3 只有 57%。

## 投影片風格

**風格基底:`intro-friendly`(科普啟蒙風)。**
選擇理由:`event-type` 是 keynote,`styles.md` 對 keynote 的預設推薦是 `keynote-impact`,
但台下有一半是沒有 ML 背景的創辦人／PM,而本場題材(評測方法論)本身門檻不低。
低門檻、留白多、比喻先行的視覺語言比「一頁一擊」更能讓兩種聽眾同時跟上。

**偏離基底的決定**:

1. **基底說** keynote 場推薦 `keynote-impact`,**本演講改** `intro-friendly`,
   **因為** 聽眾的先備知識落差比場合的儀式感更該優先照顧。
2. **基底說**「留白多、密度低,每頁最多 3 個資訊塊」,**本演講改為** 主線守此上限、
   另外允許全場 3–4 頁標為**技術頁**(右上角標、正文降一級)拉高密度,
   **因為** 講者要突顯工程實作細節且台下工程師會抓細節;明示標記讓創辦人知道這頁可以放輕鬆。
3. **基底說**「標題用問句或白話,不用術語」,**本演講**主線遵守,
   **但**技術頁標題允許術語 + 白話對照(如「二元 rubric ── 只問是或否」),
   **因為** 工程師需要能搜尋的正確名詞。
4. **基底說**「明亮溫和、飽和度中等」的自由色票,**本演講改為**沿用 POC 既有的藍與橘,
   **因為** demo 的 notebook 儀表板用的就是這組色,跨媒介必須看起來是同一套。

5. **基底說**「新概念之間要有喘息頁」,**本演講** 2026-08-19 縮短 section-04 後,
   原本 section-03→04 之間的兩處喘息頁只剩一處(section-03 末頁),
   **因為** 統計那段被移除後認知負荷峰值本身消失了,不再需要對應的喘息。

6. **基底說**「背景純白」,**本演講改為**掛主辦方提供的品牌底圖,
   **因為** 這是主辦單位的場次規範,不是設計選擇。細節見下一節「投影片分層」。

**視覺風格關鍵字**:淺色明亮、留白多、單點強調、比喻圖先於架構圖。

**色票語意**(實際色值住 `talk/src/theme.css`,本節不抄一份):

| 角色 | 用在哪 |
|---|---|
| 背景 | 純白 —— 加速器場地的投影條件不明,純白最保險 |
| 正文 | 深灰藍,比純黑溫和 |
| 次要文字 | 圖說、來源、註解 |
| 主色 | 頁面標題、段落轉場頁底色、圖形主線條(POC 藍) |
| accent | 全頁唯一的核心數字或法規警示(POC 橘) |
| surface | 卡片、表頭、程式碼區塊底色 |

改色只改 `theme.css` 的 tokens,不在單頁寫死色值;SVG 內的色碼是手抄的,改色票要跟著重抄。

### 兩個刻意的偏離,以及它們的成因

**一、背景不降透明度**(layers.md 建議壓淡,這裡維持全不透明)。
因為**主辦方 logo 是烤進這張底圖裡的**,不走前景角標;調淡背景會一起把 logo 調淡,
而那是主辦方識別,不能淡。底圖本身的色塊已經夠淺、又集中在對角,全不透明也不搶第一眼
(實作階段在最文字密的技術頁確認過)。

**二、逐頁調強弱在這份 deck 用不上。**
調弱會讓贊助 logo 變淡;在「不降透明度」的前提下調強沒有作用。
所以 layers.md 建議的「圖表頁、截圖頁、密集表格頁一律關背景」**在這裡不適用** ——
底圖夠淡,那些頁面直接沿用預設背景。

### 不放背景的頁型

- **段落轉場頁**(4 張,section-02 / -03 / -05 / -06 各一張):維持實色藍、不掛底圖 ——

  其餘 24 頁都帶 logo,主辦方曝光足夠,轉場則保留節奏的斷點。
- 其餘頁型一律沿用預設背景(理由見上面的偏離二)。

### 素材來源

- 主辦方提供的場次底圖,存於 `talk/assets/`;不是我們畫的,不改內容也不改色。
- **要根治就得換素材**:請主辦方提供「**不含 logo 的底圖** + **獨立的 logo 檔**」。

## 文字規範

執行期唯一合法的文字技法選單。`/section-impl` 與 `/page-adjust` 只能從這裡選用,不得自創;
確有規範外的需求,回 `/topic-design` 加進本節。本節只定**語意**(哪個級別用在哪個情境),
級別的實際大小住在 `theme.css`,要調大小是改 theme.css,不改本節。

### 字級(theme.css 的級別 → 使用情境)

| 級別 | 用在哪 |
|---|---|
| h1 | 封面主標、段落轉場頁的段落名 |
| h2 | 每頁頁面標題(一頁一個,固定左上) |
| h3 | 格內小標 —— 只在切格且每格需要組名時用 |
| 正文 | 條列、段落文字 |
| 技術頁正文 | 技術頁自動降一級(見「投影片風格」偏離 2) |
| small/caption | 來源、註解、圖說、圖例說明行 |

### 強調方式(每種只綁一個用途,一頁 accent 最多一處)

| 寫法 | 用在哪 |
|---|---|
| `**粗體**` | **主力**。句中關鍵術語首次出現、對比句的兩端(如「不是 X,是 Y」的 X 與 Y) |
| `<u>底線</u>` | 要求聽眾記住的結論句 —— 每段最多一句,全場不超過 6 處 |
| `<span class="accent">` | 全頁唯一的核心數字或法規警示(如 `罰 60–500 萬`、`0% → 100%`) |

術語首現一律附白話對照(基底要求),寫法固定為 **粗體術語** + 全形括號白話,
例:**二元 rubric**(每題只能答是或否的考卷)。

### 列表符號(符號 = 語意)

| 符號 | 語意 |
|---|---|
| `-` 圓點 | 無順序的並列要點;每點不超過一行(基底要求) |
| `1.` 編號 | 有先後或優先序的步驟;也用於截圖加註圖的圖例編號 |
| `✓ / ✗` | **只**用於通過/未通過的二元對照(評測結果、上線檢查),不用於一般優缺點 |

字級的實際大小、行距等排版值住在 `theme.css`(視覺數值的唯一真相),不逐頁覆寫。

## 演講風格

- **敘事型**:一條故事線帶到底(現場分裂 → 沒有判準 → 四次改版 → 數字打臉 → 你的迴圈)。
  不用「議程頁 → 一二三四」的目錄式推進。
- **語氣**:第一人稱、講自己踩的坑;保守陳述統計結論,不放寬用詞
  (「分不出差別」不等於「一樣好」)。
- **互動**:開場舉手投票(section-01)是全場唯一的強互動點;之後每段結尾用一句提問收束。
- **喘息節奏**(基底要求):新概念之間要有喘息頁 —— section-03 末頁(人工層 + 回扣核心訊息)
  是全場唯一的正式喘息頁;section-04 縮為 1 頁後本身即為低密度,section-05 的 demo 段
  整體也是低認知負荷的落地區。
- **備註密度**:每頁 1–5 行提醒,只寫要點順序、關鍵措辭、數字與時間警戒,不寫逐字稿。

## Demo 規劃

- **需要**:section-05 自成一段,9 分鐘。
- **目的**:讓「評測迴圈」從概念變成看得見的東西 —— 現場跑一次
  生成 → 三層評測 → 版本對比表,證明前面的數字不是投影片上畫出來的。
- **形式**:Colab 開 repo 既有的 `poc/` notebook(uv + python 產生),
  **全程 `OFFLINE_MODE = True` 離線重播**事先對真實 API 錄好的 fixtures ——

- **風險與備援**:場地網路不可靠時 notebook 照跑(離線);Colab 本身連不上時,
  以事先錄好的畫面截圖加註頁備援(圖形類型與頁面規劃留給 `/section-design`)。
