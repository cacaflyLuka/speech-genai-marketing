# 演講大綱與逐頁講稿

**主題**：Google Cloud & Generative AI Applications — 生成式 AI 應用整合
**副標**：從 Vertex AI Studio 到可上線的零售文案 pipeline
**日期**：2026-08-21　**時長**：45 分鐘（30 講 + 12 demo + 3 QA）
**聽眾**：新創創辦人／PM 與工程師各半

---

## 全場論點

> **生成式 AI 的難處不在叫模型，而在你怎麼知道它有沒有變好。**

這句話是軸心。它把四個原本平行的題綱串成一條因果鏈：

```
Vertex AI Studio  →  API 串接  →  Prompt 設計  →  評測流程
   （探索）          （整合）      （規格化）      （驗收）
```

**兩種聽眾各自接收到的訊息：**

| | 他們聽到的 | 他們會問的 |
|---|---|---|
| 創辦人／PM | 我怎麼知道這東西能不能上線、會不會出事 | 要花多少錢？多久？誰負責？ |
| 工程師 | 評測迴圈怎麼建、structured output 怎麼用 | 用哪個 SDK？judge 準嗎？ |

**最想被記住的一句話**（轉 3）：
> 這個 AI 功能會不會出現在你的產品定價頁上？會 → 自己做。不會 → 買現成的。

**講者自我提醒**：
- 全場只有一個主張，不要塞第二個。每一段結束前回扣主張一次。
- 遇到不確定的技術細節，說「這我要查」，不要在台上編。台下有工程師。
- 價格數字只唸 demo 當場印出來的，不唸投影片上的。

# 轉 — 整場重心（13:00 – 25:00）

## 轉 1：Prompt 不是咒語，是規格書（13:00 – 17:00）

### S9　v0 naive（13:00, 60 秒）

**投影片**：v0 prompt 全文（很短）+ 產出（很長很花）。

> 「這是大多數人第一次寫的 prompt：『幫我寫這個商品的電商文案』。
>
> 產出看起來……還行對吧？文筆不錯。
> 但它**不能用**。等一下你會看到為什麼。」

### S10　v1 加通路約束（14:00, 60 秒）

**投影片**：v1 prompt，新增的部分用色塊標出。

> 「v1 加**一件事**：約束。角色、受眾、字數上限、必須包含哪些規格。
>
> 為什麼要字數上限？因為蝦皮標題 60 字截斷。
> 你的文案再美，被截掉就是廢的。**這種事模型不會自己知道，你得告訴它。**」

### S11　v2 加法規與語調（15:00, 90 秒）

**投影片**：v2 prompt，法規段落用紅色標出 + 兩則 few-shot 範例。

> 「v2 再加**一件事** —— 其實是兩件相關的事：法規禁詞，和品牌語調的範例。
>
> 法規待會兒單獨講，那是今天最重要的一段。
> 語調的部分：**與其形容『溫和專業』，不如直接給兩則你既有的文案。**
> 形容詞模型理解不了，範例它學得會。」

### S12　v3 結構化輸出（16:00, 60 秒）

**投影片**：v3 的 `responseSchema` 程式碼 + 輸出的 JSON。

> 「v3 加最後一件事：**結構化輸出**。
>
> 注意，**不是在 prompt 裡寫「請輸出 JSON」**。那樣模型會照做九成的時間，
> 剩下一成在你上線之後才出現。
>
> 要用 API 原生的 `responseSchema` 參數。模型是被**解碼器**約束在 schema 內的，
> 不是被你的請求說服的。」

### S13　關鍵訊息（17:00, 30 秒）

**投影片**：一行大字 ——「只有 v3 能接進系統。前面三版都只是聊天。」

> 「『看起來不錯』跟『能貼進你的 PIM』是兩件不同的事。
> 前面三版都是聊天，v3 才是資料。」

## 轉 2：怎麼證明 v3 比 v1 好？（17:00 – 22:00）

### S14　三層評測（17:30, 90 秒）

**投影片**：`talk/assets/eval-pyramid.svg`

> 「現在有四個版本了。**哪個比較好？**
>
> 三層評測，由便宜到貴 —— 而且**順序很重要**。」

| 層 | 成本 | 延遲 | 能查什麼 |
|---|---|---|---|
| 規則 | 免費 | 毫秒 | 長度、格式、禁詞、必含規格 |
| LLM judge | 有成本 | 秒 | 語調、賣點覆蓋 |
| 人工 | 最貴 | 天 | 前兩層有分歧的 |

> 「**多數團隊一上來就做 LLM judge。又貴又不穩，然後放棄。**
> 先建規則層。它免費、它是確定性的、它可以進 CI。」

### S15　法規禁詞 —— 全場最重要的一頁（19:00, 2 分鐘）

**投影片**：罰則表，數字放大。

| 違規類型 | 法源 | 罰鍰 |
|---|---|---|
| 食品宣稱**醫療效能** | 食安法 §28 II | **NT$ 60 萬 – 500 萬** |
| 食品**不實誇張** | 食安法 §28 I | NT$ 4 萬 – 400 萬 |
| 化粧品**虛偽誇大** | 化粧品衛管法 §10 | NT$ 4 萬 – 20 萬 |

> 「AI 會寫出『最有效』、『奇蹟』、『逆齡』這種字。
>
> 這在台灣是違法的。食安法第 28 條，宣稱醫療效能 ——
> **罰六十萬到五百萬。**
>
> 這不是工程師的潔癖。這是你的公司會不會收到罰單。
>
> 而且注意：**AI 不知道它違法了。** 它是照著網路上幾百萬則違規廣告學來的，
> 它覺得這樣寫很正常。**你不告訴它，它就會這樣寫，而且寫得很有說服力。**」

**實測數字（50 筆評測集，講的時候要唸這組，不要唸感覺）：**

| Prompt 版本 | 法規禁詞 0 命中 |
|---|---|
| v0 naive | **76%**（約四筆有一筆踩雷）|
| v1 加通路約束 | 96% |
| v2 加法規清單 | **100%** |

> 「四分之一會踩雷。聽起來還好？**你上架十萬個 SKU，那是兩萬五千個。**
>
> 有人會說：那我 prompt 寫好一點就好了嘛。對，v1 加了約束之後降到 4%。
> **但 4% 不是 0%。** 十萬個 SKU 還是四千個。
>
> 而且 96% 這個數字本身就是我量出來才知道的 ——
> **沒有評測，你連自己有沒有 4% 的問題都不知道。**
>
> prompt 只能降低機率。**規則層才能給你保證，而且它免費。**」

> ⚠️ **這一頁是全場最有力的實證，不要講太快。**
> 76 → 96 → 100 這條線同時證明了三件事：AI 真的會違規、prompt 有用但不夠、
> 規則層是必要的。

> ⚠️ **講者注意**：這裡只講到「這是規則層要擋的東西」為止。
> 不要延伸成法規講座，也不要給法律意見。若被追問細節，
> 回答「實際商用前要讓法務或法規顧問審過，我這份清單是簡化的示範版」。

### S16　規則層能給方向，不只是擋（21:00, 30 秒）

**投影片**：`✗ 護眼 → ✓ 陪伴長時間用眼的日常`

> 「規則層不只是擋下來，還能給替代寫法。
> 這讓它從一個惹人厭的 linter，變成文案同事真的願意用的工具。」

### S17　LLM judge：不要用 1–5 分（21:00, 2 分鐘）

**投影片**：左右對照 —— 左邊「3.8 / 5」打叉，右邊一串 ✓/✗ 打勾。

> 「第二層才輪到 LLM judge，只評規則層評不了的：語調、賣點覆蓋。
>
> 但這裡有個重要的轉變。**早期大家都讓模型打 1 到 5 分。現在不這樣做了。**」

| Likert 1–5 的問題 | 後果 |
|---|---|
| 分數擠在 3–4 分 | 看不出差異 |
| 今天 4 分明天 3 分 | 不可重現 |
| 換評審模型整組平移 | 歷史數據作廢 |
| 寫得長、寫得華麗容易得高分 | verbosity bias |
| **「3.8 分」你不知道要改什麼** | 無法行動 |

> 「改成**二元判準**。把一個模糊的大問題，拆成一組具體的 yes/no 小問題。
>
> 『這份文案幾分？』→ 3.8 分，然後呢？
> 『文案有沒有寫出 30mg 這個含量？』→ 沒有 → **你知道要補什麼了。**
>
> 這也是 Vertex AI 的 Gen AI Evaluation Service 在做的事 ——
> 他們把這種判準形容成**『像單元測試』**。我覺得這個比喻很準。」

**投影片**：真實的 rubric 清單（從 demo 截圖）。

> 「而且有個關鍵細節：**rubric 是從商品資料生成的，不是看著文案出題。**
> 每個商品出一次，四個版本考同一份考卷。
> 不然就變成每個考生考不同的題目，分數根本不能比。」

### S17b　judge 的偏誤（23:00, 60 秒）

> 「還是要誠實講：**LLM judge 不是中立的量尺。**」

| 偏誤 | 這個專案的緩解 |
|---|---|
| self-preference（偏好自己的產出）| 評審模型與生成模型刻意選不同的 |
| verbosity（長的容易贏）| 二元判準 +「不因長度加分」明令 |
| position（成對比較先出現的贏）| 改用單篇對照 rubric，不做成對 |
| criteria drift（每次判準不同）| rubric 每商品生成一次，跨版本共用 |

> 「**一個會告訴你它什麼時候不準的工具，比一個宣稱永遠準的工具有用。**」

---

### S17c　實測結論：v3 沒有讓文案變好（24:00, 90 秒）

**投影片**：50 筆評測集的結果表。

| | rubric 通過率 | critical 違反 | 可直接上架 |
|---|---|---|---|
| v0 | 68.4% | 27 | 14% |
| v1 | 79.1% | 19 | 42% |
| v2 | 86.3% | 11 | **72%** |
| v3 | 86.6% | 12 | 68% |

> 「這是 50 個商品跑出來的。雜訊底線 0.3 個百分點。
>
> v0 到 v1，加十點七。v1 到 v2，加七點二。**這兩個是真的。**
>
> v2 到 v3 —— **零點三個百分點。那是雜訊，我不能說 v3 比較好。**」

（停頓）

> 「等一下，那 v3 不就白做了？
>
> 不是。**v3 沒有讓文案變好，v3 是讓文案變得可用。**
> 可機器讀取那一欄，前面三版都是 0%，v3 是 100%。
>
> 這是兩件不同的事，而你兩個都需要。」

> ⚠️ **這一頁是全場最重要的誠信時刻。**
> 你可以選擇不講、只秀漂亮的那幾欄 —— 但台下有工程師，
> 一張每格都完美遞增的表，他們看了只會覺得是調過的。
>
> **主動說「這一格是雜訊」，比任何漂亮數字都更能建立信任。**
> 而且它剛好收在你的主軸上：你怎麼知道它有沒有變好？
> 你要能同時說出「這裡變好了」跟「這裡沒有」。

## 轉 3：build vs buy（22:00 – 23:30）

**投影片**：一條分界線，兩邊各三個例子。

> 「有人會問：這些我自己做，還是買現成的？
>
> 我給一條線：
>
> **內部知識問答 —— HR 規章、IT 支援、合約查詢 —— 買。**
> 這種需求每家公司都長一樣，市面上的企業級方案兩週能上線，
> 你自己做要三個月，而且做得比較差。
>
> **但商品文案這條 pipeline —— 自己做。**
> 因為它是你的差異化，而且它必須串進你的 PIM、你的上架流程、你的品牌規範。
>
> 我給各位一句話帶回去：

> **這個 AI 功能會不會出現在你的產品定價頁上？**

## S19　降本四招（27:00, 90 秒）

| 招 | 省下 | 代價 |
|---|---|---|
| 模型選型降級 | 通常最大一筆 | **要有評測表才敢降，否則是在賭** |
| Batch API | 約 5 折 | 延遲變小時級（文案本來就不急）|
| Context caching | input token 大幅折扣 | 有門檻，前綴要夠長 |
| 結果快取 | 最被低估的一招 | 幾乎沒有 |

> 「第一招我要特別講：**降級省錢的前提是你有評測表。**
> 沒有評測表，你不敢降；有評測表，你降完跑一次就知道品質掉了沒有。
>
> **這就是評測的商業價值 —— 它不只是品管，它是你敢不敢省錢的依據。**
>
> 最後一招最被低估：**商品規格沒變就不要重新生成。**
> 很多團隊每天全量重跑，其實九成商品根本沒動過。」

# Demo（30:00 – 42:00，12 分鐘）

> ## ⚠️ 會場網路不可靠 → 用**離線重播模式**
>
> 會場 wifi 品質不佳，現場打 API 是不能接受的風險。
> notebook 內建 `OFFLINE_MODE`：**前一天在有網路的地方把真實輸出錄下來，
> 當天零網路重播。**
>
> 重播時所有 cell 一樣會執行、表格一樣是當場算出來的，只有 API 呼叫換成查表。
> 畫面上看不出差別，而且**跑得更快**（沒有網路延遲），對 12 分鐘的 demo 反而更好。
>
> **要不要跟聽眾說？要。** 一句話帶過就好，不用道歉：
>
> > 「我先說明，這些輸出是我昨天跑好存下來的，現在是重播 —— 因為會場網路我不敢賭。
> > 程式碼跟評測都是當場執行的，只有呼叫模型那一步是查表。」
>
> 台下工程師會認同這個判斷。假裝是即時的、萬一被問到才承認，才會扣分。
>
> **設定方式**：CONFIG cell 把 `OFFLINE_MODE = True`。
> 若當天網路意外地好，改回 `False` 就是真的即時跑 —— 兩種都演練過再上台。

> 重播模式下每個 cell 都是秒回，所以下表的「重跑」不需要等待時間，
> 空出來的時間留給講解與停頓。

| 時間 | 節 | 動作 | 要說的話 |
|---|---|---|---|
| 30:00 | §0 | 捲動帶過 | 「注意這幾行 —— 切 Vertex 或 AI Studio 只差 client 的參數」＋ 說明重播 |
| 31:00 | §1 | 捲動，停在 `regulated_category` | 「這個欄位是後面所有事情的關鍵」 |
| 32:00 | §2 | 秀 v0 與 v3 prompt 全文 | 「差別就是這幾段」 |
| 33:30 | §2 | **▶ 重跑 v0** | 「看起來不錯對吧」 |
| 35:00 | §2 | **▶ 重跑 v3** | 「同一個商品」 |
| 36:30 | §3 | 秀 `parse_freeform()` | 「為了評 v0，我得寫這種正則猜測的 parser。**v3 之後這段可以整個刪掉**」 |
| 38:00 | §3 | **▶ 重跑對比表** ★ | **全場高潮，停 5 秒不要說話讓大家看** |
| 38:30 | §3 | 指著 rubric 那列 | ⚠️ **主動講**「v0 比 v1 高是因為 v0 只有 8 筆受評，最爛的 4 筆被規則層擋掉了。分母不同不能比」（見下方）|
| 39:30 | §3 | 秀違規細節 + 替代寫法 | 「這不是假資料」 |
| 40:30 | §4 | 快速捲動 | 「同一套方法反過來用」 |
| 41:00 | §5 | 秀實際花費 + judge 佔比 | 「**評審佔了這麼多，這是最常漏算的**」 |
| 41:45 | — | 回到對比表 | 「所以：你怎麼知道它有沒有變好？看這張表。」 |

### ⚠️ demo 對比表上那個「看起來像變糟」的格子

12 筆 demo 的 rubric 那一列**不是遞增的**：

| | v0 | v1 | v2 | v3 |
|---|---|---|---|---|
| rubric 通過率 | **78.5%** | **74.0%** | 80.9% | 83.3% |
| 受評筆數 | **8** | 11 | 12 | 12 |

**這不是 bug，是倖存者偏差。** v0 有 4 筆被規則層擋下、沒進評分，
所以那 78.5% 只算了「活下來的 8 筆」。分母不同，兩個數字不能比。

**一定要主動講，不要等被問。** 台詞：

> 「注意 rubric 這一列 —— v0 竟然比 v1 高。是 v0 比較好嗎？
> 看旁邊『受評筆數』：v0 只有 8 筆，v1 有 11 筆。
> **v0 最爛的 4 筆被規則層擋下來，根本沒進評分。**
> 分母不同，不能比。
>
> 這就是為什麼我把受評筆數印在表上。不然這格看起來就像 v1 讓事情變糟了。
>
> 旁邊『可直接上架』那列就沒這個問題 —— 它用固定分母 12，
> 被擋下的一律算不通過。**那才是能拿來做決策的數字。**」

> 💡 這其實是全場最好的評測方法論教材：**倖存者偏差活生生出現在自己的表上。**
> 主動指出來，比表格全綠更能證明你真的懂評測。

**Demo 風險處置**（依嚴重度排序，離線重播已擋掉前兩項）：

| 狀況 | 處置 |
|---|---|
| 會場完全沒網路 | **不影響** —— 離線重播本來就不連網 |
| 網路時好時壞 | **不影響** —— 同上。這正是選重播的原因 |
| 重播找不到對應輸出 | 代表 prompt 改過但沒重錄。**演練時就會炸，不會拖到台上**（`ReplayClient` 會明確報錯）|
| 筆電當機／Colab 開不起來 | 切預錄影片（存本機，不要只放雲端）|
| 超時 | 砍 §4（場景 B），不影響主論點 |
| 有人問「這是不是造假的」 | 「錄製腳本在 repo 裡，`RECORD_FIXTURES=True` 你自己跑一次就會得到同樣的表」|
