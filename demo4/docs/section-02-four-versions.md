# Section 02:four-versions

## 段落定位

section-01 的結論是「我們沒有共同判準」。這一段先**不解決判準問題**,而是解決一個更前面的問題:
就算你有了判準,如果一次改三件事,量出來的差異也歸因不到任何一件事上。

對主軸的貢獻:核心訊息裡的「你怎麼知道它有沒有變好」有兩個前提 ——
**能量**(section-03)與**可歸因**(本段)。本段負責後者。

**討論方向**:演進脈絡 —— 依 v0 → v3 走一遍,但每一版的敘事骨架完全相同,
讓「只加了一件事」這句話重複四次、變成記憶點。

## 內容要點

1. **prompt 是規格書,不是咒語**(新知)。這段的四個版本不是「調得更好」,是把需求一條一條寫進去。
2. **v0 — 什麼都不給**(複習,section-01 已經看過它的產出)。
   `幫我寫這個商品的電商文案` 加上商品資料,就這樣。它是基準線,刻意保持這麼爛。
3. **v1 — 只加通路約束**(新知):角色、受眾、字數上限(標題 60 / 賣點 30 / SEO 120)、
   必含規格關鍵字。修的是「可上架」:長度合平台規則、規格不漏。
   **刻意不在這一版加法規** —— 一次加三件事,評測表會一次全綠,就失去歸因能力。
4. **v2 — 只加法規與語調**(新知):依商品的 `regulated_category` 動態帶入禁詞清單
   (保健食品套食安法、化粧品套化粧品衛管法),加上品牌語調 few-shot。
   這裡點一句「禁詞清單是按商品屬性套的,不是全站同一份」,細節留給 section-03。
   **加了什麼要用 prompt 原文呈現**(2026-08-20 使用者兩次要求):初版只寫「禁詞清單依商品
   屬性套用」「語調 few-shot:兩篇既有的合規文案」—— 那是**描述**不是內容,台下看不到實際被
   塞進去的法規段落與範例。改成直接放**接在 v1 後面那段 prompt 的原文節錄**:
   【法規限制】段(法源 + 禁詞例 + 帶入 60 個)、【品牌語調】段、範例 1 的標題與賣點。
   few-shot 給的是這個品牌自己既有的合規文案,一篇一組「標題 + 一條賣點」,prompt 裡共兩篇
   (晨光研選是 B群緩釋錠與甘胺酸鎂錠),不是憑空編的示範。
   **同時要回答「為什麼不跟 v1 一起加」**:一次加兩件事,下一段的評測表會一次全綠,
   就分不出是哪一件修好了哪一格 —— 那是本段的論點,不能只寫在備註裡。
5. **v3 — 只加結構化輸出**(新知,本段技術密度最高的一版):
   prompt 本身只多一句話,真正的工作交給 API 的 `responseSchema`。
   **重點是不要用 prompt 硬凹 JSON**,要用原生 structured output,模型才會被約束在 schema 內。
   **要把「兩個都寫了、但只有一個有約束力」講明白**(2026-08-20 使用者要求):
   對照 `poc/src/prompts.py` 與 `poc/src/generation.py`,v3 相對 v2 確實動了兩處 ——
   prompt 多一句「請直接輸出符合指定 schema 的 JSON」,以及 `generate(structured=True)` 設定
   `response_mime_type` + `response_schema`。但 generation.py 的註解直接寫著
   「structured=True 時啟用 API 原生的 responseSchema —— **這是 v3 與 v2 的唯一差別**」:
   prompt 那句只是保險(擋 markdown code fence),拿掉它模型一樣被 schema 綁住;拿掉 API 參數就全垮。
   頁面用三欄表格(加在哪 / 加了什麼 / 有沒有約束力)把這件事並排講完。
   **不上專案內部的變數名**(2026-08-20 使用者要求):初版表格寫 `response_schema = COPY_SCHEMA`,
   但 `COPY_SCHEMA` 只是 `poc/src/prompts.py` 裡裝著那份 schema 的 Python 變數名,離開這個 repo
   就沒有意義,台下看不出它是什麼。改成放**實際的 JSON Schema 原文**(type / properties / required),
   並點名通用語言:機制叫 **structured output**,傳進去的是一份 **JSON Schema**(公開標準),
   換一家模型商參數名不同、傳的東西一樣。投影片上只出現跨廠商共通的詞。
6. **四版,四件事**(收束):基準線 → 可上架 → 合法 → 可機器讀取。
   每一版只動一個變因,所以下一段量出來的每一格改善,都指得出是誰造成的。

7. **通路不同,前半段就是不同的 pipeline**(新知,2026-08-20 使用者要求新增)。
   `products.json` 的 `channel_limits` 裡蝦皮標題上限 60 字、momo 50 字,賣點 ≤30、SEO ≤120 兩邊相同。
   同一份商品規格要生兩種長度,所以 **v1 那段約束跟著通路換**;而 **v2 加的兩件事跟通路無關** ——
   品牌語調是品牌自己的,法規禁詞看商品屬性 —— 所以那一塊全站共用一份。
   這頁也順帶解釋了為什麼 v1 與 v2 要分開:一個會隨通路長出多條 pipeline,一個不會。
   **本輪只實跑蝦皮那條**,momo 的上限資料裡有但沒跑;被問到就照實說,換的是數字不是規則層。

**這段一個通過率都不放。** 評測要到 section-03 的三層金字塔才登場;
提早給百分比,聽眾沒有框架可以接 —— 這是實際被聽眾回饋過的問題,不要「順手補個數字更有力」。

**討論中被拿掉的點**:
- 原本打算在 v2 展開完整禁詞清單,拿掉 —— 那是 section-03 規則層的內容,
  在這裡出現會讓兩段重複,且會把「本段只談歸因」的焦點打散。

## 先備知識

- **聽眾**:需要 section-01 建立的「A 篇不能上架」印象 —— v1 修的正是那三處。
  不需要任何 prompt engineering 基礎;`responseSchema` 首次出現時附白話對照。
- **講者**:四版 prompt 的實際字串抄自 `poc/src/prompts.py` 組出來的結果,
  產出抄 `poc/data/demo_outputs.json` 重播的真實輸出,商品固定 HB-1001。
  **改過 prompt 或重錄 fixtures 之後要回來對一次**。

無。

## 頁面規劃

v1、v2、v3 各一頁,骨架完全相同:同一頁上半說「這一版只加了什麼」,下半給它的真實產出。
重複三次是刻意的 —— 版型不變,聽眾就不用每頁重新找重點位置,注意力全放在「加了什麼」上。
v0 是例外,佔兩頁:它沒有「加了什麼」可以列(它什麼都沒加),兩頁是「prompt 全文」+「產出」。

**併頁紀錄(2026-08-20,使用者要求)**:原 10 頁併成 7 頁。

  「產出長什麼樣」放同一頁,對照不必翻頁。
- **v0 的兩頁不併**(原 2、3 保留):v0 沒有「加了什麼」清單可以配對,而且它的 prompt 全文
  放得進一頁本身就是論點,砍成節錄會把那個論點弄丟。骨架仍重複三次。
- 併頁後本段一度是 8 分鐘 7 頁 = 69 秒/頁;2026-08-20 新增通路 pipeline 頁後為 **8 頁 = 60 秒/頁**,
  正好落回 `keynote-impact` 建議的 20–60 秒上緣。

## 備註要點

- **銜接**:接住 section-01 的「A 篇不能上架」—— 第 4 頁的 v1 修的就是那三處,明講這個對應。
- 每一版的「只加了一件事」都要**說出口**,四次都說,不要覺得重複就省略 —— 那是本段的記憶點。
- 第 6 頁一定要回答「為什麼不跟 v1 一起加」,並把 few-shot 的兩篇範例說成「品牌自己既有的文案」。
- 第 7 頁要講清楚:**不是用 prompt 硬凹 JSON**,是用 API 原生的 structured output。
  被問「兩個都要嗎」就照表格答:兩個都寫了,但只有 API 參數有約束力。
- 第 7 頁的 QA 防守:**schema 保證的是形狀,不是長度** —— 欄位與型別受約束,
  字數仍要靠規則層檢查。被問到就這樣答。
- **時間警戒**:8 分鐘 8 頁,平均 60 秒。v0 那兩頁最容易講太久(素材有趣),合計控制在 60 秒內;
  併過的第 4、6、7 頁各給 75–85 秒,新增的第 5 頁 45 秒。
- **交棒**:第 8 頁收在「每一格改善都指得出是誰造成的 —— 前提是你量得出來」,接 section-03。
